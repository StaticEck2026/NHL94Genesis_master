# NHL 94 segment agent

This file is the queue and the history. Do not rewrite it as a whole file. Edit it in place.

## Current rules (Oct 2026; these override older notes below)

Naming lineage is 92G -> 93G -> 94G -> 95G, and the SNES ports sit beside their Genesis parents (93S from 92G/93G, 94S from 93S plus the 94G features).
- A routine, variable or table that matches its parent takes the parent's name. 92G is the naming root.
- Clash rule: if one name would mean two different things, the earliest game's meaning keeps the name and the later one gets a new name.
- Fix the earliest repo first, then propagate the change down the lineage (92 -> 93 -> 94 -> 95, and to the SNES repos).
- Team names: 93 uses the city names of its own data; 94 and 95 use NYIslanders / NYRangers (short NYI / NYR).

Source style:
- No rename-history, provenance or origin-tag comments ("was X", "from 93G", "renamed"). That history lives in `docs/name_map.csv` only.
- No hardcoded ROM addresses in comments, and no hand-kept derived counts (sizes, numbers of entries, totals) that the code or the assembler can compute.
- Mark "new in 94" / "new in 95" only for major features, not for every changed routine.
- Local labels in 92 style: `.loop`, `.next`, `.done`, `.exit`, and plain numbers for trivial jumps.
- File headers are short plain-English stories of what the file does, modelled on `hockey93.asm`, `main93.asm` and `menu93.asm`.

Layout (SNES repos, 93S and 94S): `src/banks/` holds ordered bank files named by content (one `org`, then `incsrc` lines in ROM order),
`src/routines/<module>/<Routine>.asm` holds one routine per file, `src/data/<category>/` holds data. The folder is the module of the
routine's origin: 94G for 94 code, else 93G, else 92G; SNES-only code goes in a sensibly named SNES folder. Segment build stubs go in
`src/stubinc`, tools in `tools/`. The build runs a prebuild ROM check that names the path, file name, SHA-1 and size of the ROM it needs
(and extracts the assets automatically where the repo extracts them).

Work in small steps: every change is built and checked byte for byte against the reference ROM, then committed and pushed to main
(no force push, no PRs). Keep `docs/HANDOFF.md` current after each push.

Mod-safe build (the stock ROM stays byte-identical; see docs/ADDING_A_TEAM.md):
- `absjsr` / `absjmp` in `src/macros/genesis.mac` emit a short absolute call when the target is below $8000 and a long one otherwise. The target has to be defined already. A forward call stays `jsr` / `jmp (name).l`.
- `NoTiles` is the zero long before `TeamList`. Loads of the team list use those labels.
- The build fills $FF up to 1MB, then to 1.5MB, 2MB or 4MB if the image is larger. The header end is `RomEnd`. An include placed after the 1MB fill starts at the 1MB boundary. Content past backup RAM warns; past 4MB the assemble stops.
- `build94.bat` passes `LONGBRA=0`. If `bra.w Begin` cannot reach, it assembles again with a long jump.
- `tools/patchchecksum.js` runs after `fixopcodes` and writes the sum ValidationRoutine compares against. The source keeps the retail immediate. `tools/verify_all.sh` prints `ALL MATCH`.
- `NumTeams` and `NumPlayoffTeams` live in `src/stubinc/equals.inc`. Per-team tables are checked while assembling. A larger league moves the records block and the name log up in save RAM; the stock league does not. `TeamRatings` is aligned after its length check.

## Build

`buildseg.bat <name>` assembles `src/stubinc/<name>_stub.asm`. The stub is `org` at the confirmed start, includes `src/stubinc`, and includes `src/<name>.asm`.

`npm run seg:<name>` runs buildseg, then `tools/fixopcodes.js` on `output/<name> .lst` and `output/<name>.bin` with the org, then `tools/verifySegment.js`. The assembler listing name has a space before `.lst`.

A MATCH of 0 bytes is a failure. The byte count must be the confirmed range.

Full build check (`npm.cmd run build:retail`): delete `output/nhl94.bin` and `output/modified_nhl94.bin` first. A failed assembly writes no `nhl94.bin`, fixopcodes then fails with ENOENT, and an old `modified_nhl94.bin` stays behind and can look like a pass. Read `output/Build94.log` for errors (an undefined symbol is reported there, not as a MISMATCH). Then compare `output/modified_nhl94.bin` to `lst/nhl94.bin`: the same length (1048576) and every byte equal. Only a compare made this session counts; do not carry "byte-identical" forward from History or from Current segment.

Run the full build after every segment once `src/nhl94.asm` includes it, and after every global rename. A `seg:` MATCH only proves the names the stub equates; a name another file still uses under the old spelling breaks only the full build.

`tools/verify_all.sh` builds the full ROM and every segment and prints `ALL MATCH`. The full ROM's checksum compare is patched after `fixopcodes`; segment bins are not. A ROM that has grown is not compared to the retail image. Its size is the next of 1MB, 1.5MB, 2MB and 4MB, the header end is the last byte, and the patched checksum is the sum of the longs below ValidationRoutine.

`tools/sync.js` keeps the repo and GitHub in step (`npm run sync`; the `.claude/settings.json` hooks run it at session start, pull only, and after every turn). It commits uncommitted work on the current branch (on `main` it first moves it to a new `autosave/<date>` branch), fast-forwards branches that are behind, and pushes branches that are ahead, never with `--force`. Commits titled `Autosave uncommitted work on ...` are from it.

## Rules carried from 93

- Write real `cmp`, `cmpi`, and `exg`. `tools/fixopcodes.js` rewrites an EA `cmp.l` (`0Cxx` to `B0BC`) only. A real `cmpi.l #imm,d0` stays `0C80`. Do not revert that rule.
- Retail pad bytes win over the listing.
- A `printz` string can hide the next instruction. Write the instruction. Do not label a byte inside a string.
- If IDA splits one instruction into `dc.b` and `ori.b`, write the instruction.
- A 92 or 93 name is the field even when the 94 value differs. The equate gets the 94 value. The comment records the older value.
- Bit names (`sf2drec`, `sfwrap`) replace the number. Keep the flag word the retail bytes use.
- `jsr name` only when SNASM emits the same opcode. `jsr (name).l` is `4EB9`. `jsr (name).w` is `4EB8`. `bsr.w` stays `bsr.w`.
- A global label ends local-label scope. Strip `?` from IDA names. Keep each comment line under 200 characters.
- Do not delete an asm file. Edit it in place. Do not add a file except the stub and the segment asm.
- Data goes in the segment of the code that owns it, as 93 does: the Z80 program and sound data incbins follow the 68k driver in the sound segment, not the graphics segment. Put each data row in the ROM map with its owner from the start; moving a boundary later means changing two stubs, two `seg:` scripts and the ROM map.
- A new ROM map row gets its `include` line in `src/nhl94.asm` (in address order) in the same session. Do not leave "Full build to-do" items: a name another segment's stub equates by its IDA name, or a label another segment needs global, is fixed in that segment and its stub before the row is marked matched.
- Asset files (`tools/extractAssets94.js`, `incbin`): name each file with the 92 / 93 file name where the asset is the same one (add 94 when it differs, as `BigFont94.map.jim`), else with its label. Never an IDA address name (`unk_1AD90.bin`) or a draft name (`unknown5`). Change the extractor entry and the `incbin` line together, and check that every `incbin` path is an extractor output (old files can stay in the gitignored `Extracted` and hide a stale path).
- A map's tiles start past its 8 byte header. Write the reference as 93 does, `#SmallFontMap+8`, not an alias equate for the IDA label there. A stub that needs it equates the base (`SmallFontMap = $AAC52`).
- Team palettes are `.pal` files, as 92 / 93 teamdata: each block's `.pad` is two `incbin` lines (`..\Extracted\NHL94\Graphics\Pals\BOSh.pal`, then `BOSv.pal`, 32 bytes each, home then visitor), not `dc.w` copied from the listing. Each palette has its own extractor entry in ROM order. Name it with the 93 file name (`extractAssets93-1.1.js`: `NYIh.pal` for NYI, `NYRh.pal` for NYR, `TBh.pal`, `DALh.pal`) when the bytes equal 93's (compare against the 93 ROM, not a possibly stale `Extracted` file), add 94 when they differ (`HFDh94.pal`), and use the abbreviation for a new team (`ANHh.pal`). A `seg:` script for a segment with an `incbin` runs `npm run extractassets` first.
- Split data into the same files the previous game does, not one slice per IDA label: sound data as 93 sound93 (the Z80 driver in two parts around its FM patch bank address, one file per PCM sample, the FM patches, one file per sound and song event stream). Pointers inside the data are source, written with labels: the pointer tables (`dc.l sfx_beep1_cmdstream`), the Z80 bank address (`dc.b fm_instrument_patches&$FF,...`), loop pointers (`dc.l fmtune_eog_cmdstream+4`) and the sample table. Retail pad bytes between files are `dc.b` in the source.

## Naming rules

The style source is https://github.com/abdulahmad/NHLPA93Genesis.

- Match a function name to the NHLPA93Genesis routine when the body is the same. If the IDA name in `lst/nhl94.bin.lst` differs, keep the 93 name and put the IDA name in a comment.
- Match subroutines, arguments, parameters, and expressions to NHLPA93Genesis when the 93 source has a name for them. A 94 value may differ. The name still comes from 93.
- If you rename a label away from the lst name, note the original IDA name in the comment, only if that name is not generic (see the `;IDA:` rule below).
- Do not leave a generic name. `loc_`, `sub_`, `unk_`, and unnamed arguments need a name. Use the 93 name when there is one. Otherwise name it from what it does, in the same local-label and routine style as NHLPA93Genesis.
- Bring over the NHLPA93Genesis comment when the routine matches. If a function has no comment, add one that says what it does. Keep each comment line under 200 characters.
- These rules apply to every file a session edits, and to a file it edits to fix a mismatch. Naming is part of matching: a row is not matched while its file has an IDA auto name in code (`loc_`, `sub_`, `unk_`, `locret_`, `nullsub_`, `off_`, `word_`, `byte_`, `dword_`) or a local named by its address (`.7EA0`). Name everything in the session that transcribes the segment; a later rename pass touches every segment and stub again.
- IDA placeholder names are generic too: `noidea`, `Unk_ControlsSetRelated`, `nullsub_2`. Name them from what the code does.
- Every renamed label keeps its exact listing name in an `;IDA:` comment on its definition line, only if that name is not generic (`GetPeriodTime	;IDA: ClockLength`, `ValidationRoutine	;IDA: Calc_Checksum`, `.ret	;IDA: _exit`). A generic listing name is not noted: an IDA auto name (`loc_`, `locret_`, `sub_`, `unk_`, `nullsub_`, `off_`, `word_`, `byte_`, `dword_`, also `#(loc_x+4)` style operands) or an IDA placeholder (`noidea`, `Unk_ControlsSetRelated`). A label the listing does not have gets no note either (no `no IDA label`), and a RAM expression comment line is just `;$addr is expr`. Look the name up in `lst/nhl94.bin.lst`; do not guess it. A comment that refers to another routine uses its label, not its IDA auto name.
- Locals: where the routine matches 93, line up the instruction sequences and take the 93 local at the same instruction (menu93 `.1`, `.flip`, `.x`). Elsewhere use the 93 local style: `.x` for an exit (`rts`, or `movem.l (sp)+` then `rts`), `.loop` for the target of a later branch back, else `.0`, `.1` ... in order within the routine. A local name must be unique in its global scope.
- If 93 has a global where 94 has a local (93 LineEditorMenu, SelectAttributeItem, DisplayPlayerSelectMenu inside one 94 routine), make it the 93 global. A label two routines reach across a global label is global; name it for its routine (`doinput_ispc`).
- Data labels are named too: tables (`OneTimerNearTbl`), Strings (`RecByTxt`), SPA tables (`SPAboardleft`, not `SPA_18CC`). An unreferenced IDA label inside data or a String is not a label.
- Expressions: where a 94 instruction lines up with a 93 one and 93 writes a symbol (`tmdata(a2)`, `#tmsize`, `#pfgoal,pflags(a3)`, `#dfng`), write the 93 symbol only when it evaluates to the same 94 value under the stubinc equates. If the value differs, keep the number. A 93 name that is missing from stubinc gets added there with the 94 value. Do not substitute in code that does not line up with 93.
- SNASM symbols are case-insensitive. Check a new name against every symbol in `src` and `src/stubinc` ignoring case (IDA's `FaceOffsprites` was 93 `linelist`, and it blocked 93 `FaceOffSprites`).
- A rename changes code and comments, but not an `;IDA:` note and not an `incbin` path. After it, reread the comments it touched: no `X (93 X)`, no `X X` where a comment listed "IDA name, 93 name", and file headers describe the naming the file really uses.
- The 93 structure, team, game and flag names (`Ypos`, `SCnum`, `pflags` / `pfteam`, `tmap`, `tmsize`, `gsper`, `sfhor` ...) are in `src/stubinc/equals.inc` with the 94 values (`tmsize` is `$364`, 93 `$1A2`). Write `Ypos(a3)`, not `$14(a3)`.
- A global rename changes every file that uses the name: the segment asm and the `_stub.asm` equates (SNASM symbols are case-insensitive). Then rerun every `seg:` script and the full build.
- RAM names: use the 93 name at the same address (94 RAM up to `$FFBDB0` is laid out as 93 `ram93.asm`), or the 93 name of the operand in a lined-up 93 instruction. A field of a structure is the 93 expression, not a name: `SortCords+OldXpos`, `SortCords+(puckscnum*SCstruct)+attribute`, `HmShots+tmgoalie`, `palfadenew+$40`, `gameclock+2`, `Z80_RAM+$8E`. Otherwise name it from what it holds. An equate nothing uses is a comment line, not a name.
